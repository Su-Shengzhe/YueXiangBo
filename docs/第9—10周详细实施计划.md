# 第9—10周详细实施计划：交易、退款、结算与对账

编制日期：2026-10-28；版本：V1.1（工时复估、分段交付与恢复验收优化）；执行状态更新：2026-10-29已启动，G0未通过。责任人：学生开发者；指导教师参与阶段评审。实际进度见[实施基线](第9—10周需求与实施基线.md)及[验收记录](../第9—10周实施与验收记录.md)。

本计划承接[项目计划](../项目计划.md)第8.2节，按正式启动后的第9、10周安排，不将编制日期直接作为第9周起点。每周按5个工作日编排，实施24小时、机动缓冲2小时；两周合计实施48小时、缓冲4小时。实际日期待正式周次日历确认后填入，实际工时单独记录。48＋4小时是原预算基线，不是已经验证可行的完工估算；第2日必须完成首次复估，满足容量及前置条件后才能沿用后续日程。

本次修订保留M3范围和资金正确性标准，将故障测试能力提前建设，按业务流程同步完成最小页面，保护末期9小时验收、修复及复测窗口。修订不表示代码、迁移或用例已经执行。

## 1. 阶段目标与当前起点

本次规划查阅了项目计划、后端与数据库设计、当前交易代码及[第7—8周验收报告](第7—8周迁移并发与负载验收报告-2026-10-27.md)。没有重新运行业务测试，以下“已有”指代码或历史报告提供的起点，不代表当前版本已经重新验收。

## 2. 开工条件与工作包预算

第9周第1日先核查M2交接：现有版本能从网关完成预约、支付确认、入离场及账单生成；关闭预约后的补偿事件可恢复；停车事件重复或乱序不会回退交易投影。需要资金集成的任务必须以该检查通过为前提，接口设计和页面准备可以继续。

如发现阻断缺陷，登记为M2遗留任务并单列剩余工时和负责人。4小时阶段缓冲按需使用，不限定每周必须各用2小时；预计不足时重排M3日期，不能把M2缺口记为已完成，也不能删除资金正确性测试以维持日期。

### 2.2 第2日复估与日程调整规则

第1日逐项检查“可直接复用／需改造／需新增”，为每项记录代码或既有证据；缺少证据的项不能按直接复用估计。第2日结合支付和故障适配的实际工作量，填写以下复估记录，并在第9周末及第10周第3日更新：

|---|---|
| 子任务及归属 | 含M2遗留、故障适配、迁移、页面、测试脚本、修复与复测；避免重复计费 |
| 实际投入A | 已发生的有效人工小时；未知工时标待补录，不能填预算替代 |
| 剩余估算E | 分开发、迁移、测试、页面与联调，填写正常和不利情况下的估算及依据 |
| 预计总投入 | A＋E；与48小时实施基线及52小时含缓冲上限分别比较 |
| 日历容量 | 依据剩余可用人工小时；不默认学生可以加班或借用AI阶段工时 |
| 处置与日期 | 保持日程、使用多少缓冲，或新增多少小时及顺延后的候选/验收日期 |

末期9小时必须保留，其中第10周第4日5小时用于集成专项与修复，第5日4小时用于复测、演示和归档；这些工作计入48小时，不与T09或基础测试重复加总。因此原日程中范围开发、分段测试和候选版本准备合计最多39小时。若前两日实际使用10小时，后续候选版本准备仅余29小时；这只是容量计算，不是完成能力判断。

复估时若候选版本所需剩余工时超过其剩余容量，或总投入预计超过52小时，应立即给出差额、关键依赖及新日期，并同步总计划的M3和第11—12周依赖安排。在日历未确定时先按工作日顺延，不能虚构具体日期。范围未完成则延后候选版本和验收窗口，不占用末期9小时补开发，也不降低必测标准。原基线和复估结果同时保留供比较。

## 4. 各工作包实施要点

### 4.1 数据与契约（T01）

1. 明确当前`trade_order`、`payment_attempt`、`channel_operation`、`ledger_entry`与目标表的差异；逐项定义应收单、成功收款、退款父单/明细、争议、结算批次/项/尝试、调整及对账差异。
2. 采用新增Flyway迁移，不覆盖已执行的trade V001/V002；具体新版本号以执行时目录为准。优先增加结构、回填、校验后再切换读取，保留旧业务号与流水关联。
3. 历史成功支付只能基于可核验的通道记录和流水建立收款事实，不因存在支付尝试就视为成功。业主、服务费率和规则版本从原预约快照或可信历史记录补齐；无法确认的记录列入差异并阻断结算，不按当前配置猜填。
4. 对存量CREATED/SUBMITTED/UNKNOWN/REVIEW任务制定迁移映射；停写并暂停资金任务后进行切换，避免旧worker和新worker重复执行。不能靠删除在途任务解决迁移问题。
5. 固定外部`reservationId`及字符串ID、整数分金额、`billVersion`、状态枚举和错误码；事件包含唯一事件号、聚合版本及可追溯业务号。
6. 当前`/api/v1/bills/{id}`、`/api/v1/payments`、`/api/v1/payments/{id}`与设计接口存在差异，形成保留、适配或迁移清单，更新`docs/openapi.yaml`和前端调用，保证旧演示可回归。

迁移实施与演练归T08：第9周第4日在隔离环境用实际存量备份完成首轮切换/恢复演练，覆盖成功记录及CREATED/SUBMITTED/UNKNOWN/REVIEW任务；第10周第3日对包含结算、对账等全部新增结构的候选版本再演练。首轮成功不能代替最终结构验证。夹具须保留真实关联，不能只改单个状态制造虚假的合法在途记录。

每次演练依次记录：停止入口写入和定时任务/消费者→等待或登记在途操作→一致性备份及校验→新增迁移和映射→资金总额、业务号、活动任务核对→启动单一新版本任务→原号恢复→四角色冒烟与对账。任何校验失败均保持停写，先保留失败现场，再按预先登记方案恢复。

迁移方案必须注明新旧程序兼容范围和恢复条件。仅确认向后兼容时才允许旧程序重新接入；不通过倒退Flyway版本或直接启动旧worker进行回退。在隔离演练中恢复备份须连同相关服务库、模拟通道事实和待处理消息清单一起核对；若切换后已经产生新资金事实，不能仅恢复业务库抹去这些事实，应保持停写、核验通道原号并前向修复。恢复验证通过后才开放写入。

### 4.2 可控模拟通道与故障设施（T02先行）

当前正常模拟通道直接落SUCCESS，只能作为正常路径起点。下列设施先于支付、退款及结算恢复验收建立，退款和结算接入时复用适配接口，不能在最后一天临时编写：

| 能力 | 最小交付与检查 |
|---|---|
| 结果控制 | 可指定成功、确定失败、未知和延迟；请求超时与通道最终成功独立，支持响应丢失后按原号查询 |
| 持久通道事实 | 业务号、操作类型、金额、结果可查询；记录请求/查询次数与有效资金动作次数，重复请求不能重复资金动作 |
| 确定性故障点 | 复用`PAY_AFTER_CREATE_COMMIT`、`PAY_AFTER_CHANNEL_SUCCESS`、`REFUND_AFTER_RESERVE_COMMIT`、`SETTLEMENT_AFTER_FAILURE_COMMIT`；结算另补“通道打款成功、业务未落库”故障点 |
| 可观察执行 | 到达故障点发出可核验信号，再停止指定测试服务并重启；不依赖随机sleep碰撞窗口；记录旧/新租约token与原业务号 |
| 时间与重试 | 区分业务时间、调度时间及真实超时；分别验证5次查询退避、租约接管和超限人工核查，扫描循环不能绕过次数上限 |
| 环境隔离 | 仅test/demo显式启用，普通支付参数不能控制结果；非测试配置验证故障入口关闭，清理仅针对本次隔离数据 |

第2日准入至少要实测支付原号恢复及成功/失败/未知路径，冻结退款/结算适配契约。其余领域故障点与对应模块同日实现、同日验证。设施建设、领域接入和专项运行分别记账，新增工作超出原T02预算时如实复估。

### 4.3 支付与退款（T02、T03）

- 区分应收、支付尝试和真实收款。每项应收最多一个活动尝试；更换客户端幂等键不能绕过活动限制。第二笔真实成功收款仍登记事实，并进入多收补偿。
- 取消、超时、未到场及无法履约的自动退款接入统一引擎；用户争议申请使用完成/关闭后7天窗口，达到截止即拒绝。同原因同事实返回原申请，驳回后仅期限内新增证据允许关联重提。
- 审批和执行分别记录状态；同订单同时最多一个待审批或执行中争议。未决争议、在途退款均阻断结算。
- 每次退款同时检查订单总额、单笔收款额度和父退款批准目标；在交易锁内预留并创建明细，通道调用在事务外执行。未知保持预留，确定失败释放，成功同步记账和结转。
- 重试仅针对确定失败明细，重新检查可退额度；用唯一后继关系防止并发重复重试。部分成功按实际明细汇总，不提前把父退款或争议标记完成。
- 复用持久任务和租约，资金未知结果按5、10、20、40、60秒查询5次；耗尽后人工核查，保持活动资格或预留。原号查询与重发遵循既定通道幂等条件。

### 4.4 收益与结算（T04）

- 净实收N＝成功收款－成功退款；平台累计份额F＝HALF_UP(N×订单比例)，业主份额O＝N－F。使用精确十进制、整数分，份额调整取新旧累计值之差。
- 仅停车完成、全部应收结清、无在途退款、未决争议、未解决差异或多收补偿时允许结算。预览列出可结与阻断原因，执行时在同一交易锁下重查资格和金额。
- 一个订单只有一个普通结算项；批次逐项事务，成功项不会因其他项失败而重付。每次打款保存不可变金额、账单版本和业务号，未知状态只查询原号。
- 结算处理中可接受争议申请但延后审批退款；打款确定失败后，先处理争议，再重核当前金额创建新尝试，旧尝试不改写。
- 已结算后退款只追加份额调整和待追回记录。待追回展示原结算、退款和余额关联，不执行真实追款或自动抵扣。
- 资格满足但业主份额为0时，记录零额结算成功与原因，不发起零元打款。

T01先定义阻断字段、差异集合及其事务归属，T04实现结算时的锁内校验，T05接入完整检测与复查，避免“结算等待对账、对账又等待结算”的实施依赖循环。T05未完成时，结算只能在隔离夹具上验证，不能据此认定结算闭环已验收。

### 4.5 对账、通知、统计与审计（T05、T06）

按数据库设计实现R01收款汇总、R02退款汇总、R03三层预留、R04份额守恒、R05打款及结算一致、R06关闭补偿/多收/未知、R07退款目标及重试链、R08活动尝试指针共8类检查。每条差异保存规则编号、订单、期望值、实际值、发现时间、复查结果及处理意见。

发现差异即阻断受影响订单结算。处理仅调用原业务恢复入口，复查确认一致后才解除阻断；禁止提供直接编辑流水、强制结算或只填写“已处理”即放行的入口。重复运行同一检查不应生成大量重复未解决差异。

对账与结算并发遵循以下约定，具体SQL及锁顺序在T01契约中固定：

1. 单订单本地资金事实在短事务内按统一交易锁读取，记录`basisBillVersion`；不得把不同时间的多次查询拼成一次对账结果。涉及跨服务或模拟通道的查询在锁外进行，并记录事实标识和查询时间；事实未齐全时标记待核查，不以异步延迟认定账本损坏。
2. 将检查结果用于新增差异、解除阻断或启动结算前，重新取得交易锁，检查账单版本及当前全部未解决差异。版本变化则放弃旧结论并重新核验；外部证据不足不得解除阻断。
3. 复查一条差异通过不等于订单已无差异；仅全部未解决差异清除、且相关资金事实仍满足约束时解除对账阻断。退款、争议、多收等其他阻断独立检查。
4. 结算执行在锁内重验可用本地事实、金额守恒、活动尝试和阻断条件，不能只相信上次对账通过标记。对账晚于结算发现差异时保留已发生打款事实，阻止新的结算执行并进入核查，不回写成“未打款”；原号查询、合法退款及必要的补偿仍通过受控恢复入口执行，不因对账阻断而停止纠错。
5. 增加对账读取中退款、复查时新增差异、复查与结算并发、多差异仅解决一条等用例。资金变化必须更新可用于核验的版本，差异集合变动也受同一交易锁保护。

站内消息覆盖预约、占用异常、退款和结算，按事件及接收人去重，仅本人可读或标记已读。订单量由停车服务提供，净实收与业主份额变动由交易服务提供；固定筛选时间字段、时区及`asOf`，展示统计口径。业主只能看本人收益，物业不得越权读取平台资金数据。

历史订单在本期退款时，订单量仍归订单创建期，退款和份额调整计入资金发生期；两个服务分别返回自己的`asOf`，不宣称跨服务统计属于同一原子快照。对应TC38-03核验负向金额、时间边界与角色权限。

退款审批、结算执行与重试、差异复查、人工恢复写操作者、对象、原因、结果、时间和traceId；成功审计随业务事务提交，拒绝记录单独保存。审计字段脱敏。

### 4.6 页面与AI交接（T07、T08）

复用现有页面壳、表格、表单和详情抽屉，完成P03账单、P06退款、P09收益、P13结算、P14对账、P15审计、P17通知以及三类统计卡片。平台审批与争议处理放在管理工作台授权标签页。

金额使用后端返回值；区分支付成功/预约确认中、退款审批通过/执行中/成功/部分成功/待核查、结算受理/执行中/部分失败。提交超时先按原请求或业务号查询，不以刷新或更换幂等键盲目重做。页面覆盖加载、空数据、失败、无权限及处理中状态。

每段页面交付必须验证“请求已受理但响应丢失”“处理中刷新”“令牌失效后重新登录”“账号A切换B”。恢复数据绑定用户及业务类型，换账号清除旧恢复元数据，后端仍强制归属校验。退款、审批、结算等新增写入沿用原请求或业务引用恢复，不能把支付页面测试结果直接当成其他资金页面通过。

为第11—12周提供稳定本人账单输出：费用分项、价格和规则版本、收退款记录、净支付、资金状态和`billVersion`；服务端校验本人归属，不接受模型指定用户身份。准备正常、超时、部分退款及结算后退款四类脱敏样例。

## 6. M3演示脚本与完成标准

以受控演示日和测试时钟运行以下流程，生产配置不得暴露时间推进或强制结果开关：

1. 业主发布每小时4元的车位，物业审核并开放共享窗口。
2. 司机预约09:00—11:00，支付800分并确认预约。
3. 09:00入场、11:20离场，补缴200分；总成功收款1000分。
4. 按10%比例显示平台100分、业主900分，管理员预览并执行模拟结算。
5. 司机在允许期限内申请退200分，管理员批准，等待退款真实成功。
6. 展示净支付800分、平台累计80分、业主累计720分，以及业主待追回180分；原900分结算记录保留。
7. 执行对账，查看资金一致性、消息和审计；待追回作为合法业务状态展示，不当成账本损坏。
8. 独立故障样例演示一次未知退款或未知打款的原号恢复，以及差异阻断结算和复查解除。

M3通过需同时满足：上述演示可复现；18组W910及其必需子用例全部通过；资金差额为0分；无越权、重复收退款/打款、金额错误、丢失资金事实等严重缺陷；空库、存量切换及恢复可复现；操作文档、源码版本和证据对应最终验收版本。修复后重新构建，按影响范围重测，资金状态机、迁移、共享锁或消息机制变化须重跑相关并发和恢复组；不能将旧版本通过结果直接作为新版本证据。一般界面缺陷需列明影响和修复安排，任何未验证核心项都不能写成整体通过。

| 工时与容量不匹配 | 第2日G0或周末G1未达成，或候选准备/总投入超过剩余容量 | 当日更新A＋E与差额；保留末期9小时，重排候选和验收日期并标明AI阶段依赖影响 |
| 故障设施不足 | 无法稳定产生失败/未知或无法观测崩溃窗口 | 优先补齐适配与信号，不使用随机sleep或手改成功状态冒充恢复测试 |
| 对账结果过期 | 读取后账单版本或未解决差异集合变化 | 放弃旧通过结论，锁内重核；事实不齐保持待核查，不自动解除阻断 |
| 未知资金结果无法收敛 | 自动查询次数耗尽 | 转人工核查，保留预留和活动指针；不盲目更换业务号 |
| 页面工作超时 | T07预计超过6小时 | 复用表格与抽屉、简化样式，不削减必要状态、权限和恢复入口 |
| 候选版本不完整 | 第10周第3日G2未达成或脚本不可运行 | 顺延整个验收窗口，不用第4—5日补建模块；明确未完成项与预计新增工时 |
| 测试环境不可用 | Docker、MySQL或消息组件无法启动 | 记录环境阻塞；继续单元测试和文档，恢复后补足实库与整链证据 |

本阶段不重复开展第7—8周全部负载测试，也不将其事务层吞吐当作交易端到端性能。本阶段聚焦资金正确性和故障恢复，全量性能、AI隔离与论文对照实验仍按第13—14周安排。
